- Werktijden (werkplaats_werktijden) zijn de enige bron voor gewerkte tijd: src/lib/workHours.ts knipt intervallen af en werkplaats_auto_pauze (cron elke 15 min) pauzeert op de eindtijd — zo tellen doorgelopen timers niet als uren.
- Poets-werkorders worden door werkplaats_auto_pauze alleen automatisch gepauzeerd als system_config.werkplaats_auto_pauze_poets = 'aan' (standaard 'uit'): de gepubliceerde app heeft nog geen Hervatten-knop voor poetsers, dus auto-pauze zou ze vastzetten. Zet de sleutel op 'aan' zodra er gepubliceerd is met de poets-pauze.
- Leenauto's toevoegen/bewerken/uit gebruik nemen gaat alleen via de SECURITY DEFINER RPC's leenauto_toevoegen/leenauto_bijwerken/leenauto_deactiveren (rolcheck leenauto_mag_beheren, gelijk aan LEENAUTO_MANAGE_ROLES): zo hoeven vehicles-/loan_cars-RLS niet breed open. Voorraadauto's als leenauto houden hun vehicles.status (bron='voorraad'); leenauto's worden nooit verwijderd maar op actief=false gezet, zodat de historie blijft.
- Klant zoeken bij uitlenen gaat server-side via leenauto_klant_zoeken (ook op kenteken/merk/model/VIN van gekochte en werkplaats-auto's); een handmatige klant opslaan in het CRM gaat via leenauto_klant_opslaan.
- Medewerkers met historie worden nooit hard verwijderd: delete-user weigert (409) als public.medewerker_historie iets vindt; uit dienst zetten gaat via edge function user-deactiveren (ban + sessies weg + rollen weg + profiles.actief=false). Waarom: tasks/task_history staan op ON DELETE CASCADE en zouden stil verdwijnen.
- Werkhistorie per auto komt uit één SECURITY INVOKER RPC voertuig_werkhistorie (werkorders ook van andere records met hetzelfde VIN/kenteken ≥6 tekens, plus claims); split vóór/na aflevering op NL-kalenderdag via src/lib/workHistory.ts. Waarom: bestaande RLS blijft gelden en één query per dialoog.
- Omzet komt overal uit één bron: RPC `omzet_regels(van, tot, branch)` (SECURITY INVOKER) + `src/lib/omzet.ts` (zelfde regels als pure functies, met tests). Tak/omzet_datum op workshop_invoices worden door trigger `workshop_invoice_fill_omzet` gevuld. Waarom: schermen telden eerder met verschillende datums/koppelingen en sloten niet op elkaar aan.
- Revenue screens use the shared read-only liveOmzetRegels projection of invoice rows plus disjoint pending internal polishing orders; invoice controls keep original rows separate. Why: monthly invoicing must not delay revenue or duplicate employee allocation.
- Customer editing controls use canEditContact separately from the general director read-only helper, while contacts RLS remains unchanged. Why: director customer corrections are allowed without enabling unrelated writes.
- website-reservering edge function: own secret header auth, idempotent on betaling_id via website_reservering_log unique index; matches vehicles only by exact VIN then normalized plate, never guesses. Why: public site calls it without user session.
- B2C branch dashboard and target editor share defaults in src/lib/b2cTargets.ts; the absolute margin KPI adds warranty revenue once while the vehicle margin percentage remains unchanged. Why: targets and their progress must use consistent definitions without changing the separate upsales metric.
- Customer editing uses the existing contact form and direct contact update with additive RLS limited to B2B/B2C for aftersales leadership; supplier, transporter, creation and deletion permissions stay separate. Why: customer corrections must not grant unrelated contact management rights.
- Warranty work-order creation uses garantie_werkorder_inplannen for atomic role/branch-checked claim, vehicle and order linking; manual vehicles are workshop-only and customers are explicitly selected, never inferred from names. Why: work_orders requires a vehicle and separately saved CRM contacts do not link themselves to manual claims.
- Vehicle history timeline comes from one read-only SECURITY INVOKER RPC voertuig_tijdlijn (per-source EXCEPTION WHEN insufficient_privilege blocks; amounts filtered by has_role in SQL, never only in the frontend); display logic lives in src/lib/tijdlijn.ts with tests. Why: every role sees the same timeline with only the sources and amounts their role allows.
- "Geen factuur nodig" on work_orders is set only via SECURITY DEFINER RPCs werkorder_factuur_niet_nodig / werkorder_toch_factureren (owner/admin/aftersales_manager); the open-invoice selection (src/lib/externFactuur.ts, omzetService, extern_facturen_open_aantal) excludes marked orders. Why: work_orders UPDATE-RLS stays narrow and the count stays consistent across screens.
- Warranty numbers are allocated by a locked yearly counter trigger and never replace UUID foreign keys; contact changes use an atomic SECURITY INVOKER RPC and an audit trigger. Why: numbering is concurrency-safe and contact-card RLS remains authoritative.
- Vehicle open points use a separate SECURITY INVOKER RPC shared by all timeline views. Why: read-only status summaries respect each source's existing RLS without per-card queries.
- Warranty-claim loan car display uses only leenauto_uitleningen.warranty_claim_id (src/lib/claimLeenauto.ts), never the pool car's current loan; claim-side returns pass p_warranty_claim_id to leenauto_innemen. Why: loan_cars are reused pool cars, so their current borrower belongs to other claims.
